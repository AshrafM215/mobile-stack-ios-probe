# Handover: candidate B (React Native)

NON-PRODUCTION / SYNTHETIC DATA ONLY.

## 1. What this application is

Candidate B is a wayfinding application for a set of synthetic buildings: its home screen has a search field, a result list, three floor buttons and a map. A result opens the destination details with a schedule, and the details open a route screen with a start entrance, a step-free switch and a computed route (summary and numbered text steps). From a route the user opens AR, which is a native full-screen AR screen or, where AR is not supported, a text fallback screen. The application also scans anchor codes (QR), has a data and trust screen with a lab update, and switches between Arabic and English at run time. All data is synthetic: the bundle `synthetic-data/out/bundle/G1SYN-1.0.0.zip` is embedded in every build, and nothing is for navigation. The code is TypeScript on React Native 0.87.1 (React 19.2.3, New Architecture, `hermesEnabled=true`), with Kotlin and Java on Android and Swift and Objective-C++ on iOS.

### 3.2 iOS

The lab host has no macOS toolchain. The iOS path is built and tested by a job on a hosted macOS runner: `ios-ci/workflow/g1-ios-feasibility.yml` (`runs-on: macos-26`, Node 24.13.1) calls `ios-ci/run-job.sh` with the job name `candidate-b-react-native`, which runs `ios-ci/probe-candidate-b-react-native.sh` with the helpers of `ios-ci/probe-common.sh`. A failed stage does not end the job. A stage whose needed stage did not pass is recorded as skipped. The job exits non-zero when any stage failed or was skipped. The stages, in order:

1. `environment`: selects the pinned Xcode 26.6, records the runner, creates and boots the simulator (device type `iPhone-17`, runtime `iOS-26-5`), runs `ios-ci/prepare-data.sh` and fetches XcodeGen 2.46.0. `ios-ci/prepare-data.sh` regenerates the dataset, checks it against `synthetic-data/out/GENERATION_RECORD.json` and calls `ios-ci/prepare-assets.sh`, which copies the bundle, the trust store and the lab CA into `native-common/ios/Sources/G1NativeCommon/Resources/g1`.
2. `resolve`: `npm ci --no-audit --no-fund` in `candidate-b-react-native`; `pod install --deployment` in `candidate-b-react-native/ios` (CocoaPods in deployment mode: the lock file may not change); `xcodebuild -workspace ios/G1CandidateB.xcworkspace -scheme G1CandidateB -resolvePackageDependencies` with `-disableAutomaticPackageResolution` (Swift packages at the versions of the resolved file).
3. `configure`: `xcodebuild -list` must list the scheme `G1CandidateB`.
4. `unit`: `npx tsc --noEmit` (type check), then `npx jest --ci --json` (the same unit suite as on Android).
5. `build-simulator`: Release build with `-sdk iphonesimulator` and `CODE_SIGNING_ALLOWED=NO`, with the embedded JS bundle; derived data in `candidate-b-react-native/ios/build/dd`.
6. `linkage-simulator`: `otool -L` over the built app. The stage fails unless MapLibre and ARKit are linked.
7. `launch`: installs and launches the app on the simulator and waits for the marker `app.ready`. It passes only when these markers appear in this order: `app.start`, `bundle.loaded` with `state=VALID`, `map.style.loaded`, `app.ready`.
8. `e2e`: the UI flow `ios-ci/e2e/G1E2ETests/FlowTests.swift` against the bundle id `com.example.g1bench.candidateb` and the URL scheme `g1bench-b`: search, details, route, AR fallback, language switch, largest text size, and an injected anchor code (`synthetic-data/out/qr/A01.png`) through the lab URL.
9. `build-device`: Release build with `-sdk iphoneos` for a generic iOS device, unsigned; derived data in `candidate-b-react-native/ios/build/dd-device`.
10. `linkage-device`: the same linkage check on the device app.
11. `inventory`: the Swift packages and the pods with their licence texts.
12. `lock-check`: each of these lock files must be tracked and unchanged, and no other lock file may be untracked or changed: `synthetic-data/package-lock.json`, `candidate-b-react-native/package-lock.json`, `candidate-b-react-native/ios/Podfile.lock`, `candidate-b-react-native/ios/G1CandidateB.xcworkspace/xcshareddata/swiftpm/Package.resolved`.

The job has a second mode, `G1_RESOLUTION=update`: `pod install` runs without `--deployment`, package resolution may write the lock files, and a changed lock file does not fail `lock-check`. The Swift suite of the shared native module runs in a separate job, `ios-ci/probe-native-common.sh`.

## 4. How it works

**State.** One `AppState` (`candidate-b-react-native/src/state.ts`) is created in `candidate-b-react-native/App.tsx`. It holds all state as plain fields: language, bundle info, parsed bundle data, search index, route graph, map style, screen stack, floor, search text and results, route inputs and result, anchor-code outcome, update status. It is an external store. `App` reads it with `useSyncExternalStore(state.subscribe, state.getSnapshot)`. Every handler changes fields and calls `notify()`, which raises the revision and causes a render. `App` calls `state.onCommit()` in a layout effect after every commit; `nextFrame()` uses it to wait for the second `requestAnimationFrame` after a commit (the frame rule of the contract). The UI and the lab hooks call the same handlers.

**Screens and navigation.** There is no navigation library. `AppState.stack` is a list of `ScreenEntry` values (`home`, `details`, `route`, `fallback`, `qr`, `settings`); `push`, `back` and `goHome` change it. `Root` in `candidate-b-react-native/src/ui/screens.tsx` renders the top entry. `HomeScreen` with its map stays mounted under the other screens and is hidden with `display: 'none'` while it is covered. The hardware back key calls `state.back()` when the stack has more than one entry. A push writes the marker `screen.shown` with `screen` = `S04` (details), `S07` (route), `S09` (fallback), `QR` or `SETTINGS`; a return to home writes `S01`. Every contract id of these screens (`ids` in `contract/contract.json`) is a `testID`; the ids `ar.status`, `ar.arrow` and `ar.close` belong to the native AR screen of the shared module.

**Ready sequence at launch.**
1. The native module is created. `G1Native.init` (Android) or `G1Native.initialize` (iOS) loads the trust store and writes `app.start`.
2. `App` calls `state.boot()`. `ensureBundle` installs the embedded bundle on first launch through the full trust check of the shared module and verifies the active bundle again on every load. It writes `bundle.result` (first launch only) and `bundle.loaded` with `state` and `version`.
3. `loadData()` continues only when the state is `VALID`. `BundleData.load` reads the bundle files `destinations.json`, `graph.json`, `schedule.json`, `route_cases.json`, `query_corpus.json`, `style.json` and `geometry.geojson` through `readBundleFile`. Then `AppState` builds the `SearchIndex`, the `RouteGraph` and the split map style (`splitStyle`). A parse failure writes `bundle.loaded` with `state=PARSE_ERROR` and leaves the application without data.
4. `HomeScreen` calls `state.homeShown()` two frames after it is mounted with the search field enabled. The map calls `state.onStyleLoaded()` from `onDidFinishLoadingStyle`, which writes `map.style.loaded` with the floor.
5. `checkReady()` sets the ready flag when home is shown, the style is loaded, the bundle is trusted and the index exists. On the next frame `reportReady` writes `app.ready` in the shared module (Android also calls `Activity.reportFullyDrawn()`).
6. `LabController.start()` subscribes to commands and AR events, waits for ready (at most 60 s) and then runs the launch command, if there is one. A return to the foreground writes `app.resume.ready` (`state.onResumed()`).

**Search and route.** `submitSearch` runs `SearchIndex.search(state.query)` and stores `results`. `openDetails` pushes the details screen. `openRoute` pushes the route screen and clears the old route. `computeRoute` calls `RouteGraph.route(origin, destination.node, stepFree, blocked)`; for the outcome `PATH` it calls `routeSteps` and stores `route`, `steps`, `summary` and the map line `routeFc`. Without a trusted bundle the search returns no match and the route outcome is `REJECT_UNTRUSTED`. Both handlers return their compute time in nanoseconds for the lab hooks.

**Anchor codes, AR, update.** `scanQr` opens the native scanner and passes the payload to `validateQr`; `QrScreen` shows the outcome. `openAr` pushes the fallback screen unless `arAvailability` is `SUPPORTED` or a lab script is injected. Otherwise it calls `startAr`, and `setArGuidance` when `guidanceAllowed` is true (trusted bundle and a route with the outcome `PATH`). `update` downloads a container from the lab origin and imports it with `importBundleBase64`; `afterBundleChange` then loads the data again.

**Map.** `MapPanel` (`candidate-b-react-native/src/ui/MapPanel.tsx`) uses `Map`, `Camera`, `Layer` and `GeoJSONSource` of `@maplibre/maplibre-react-native`. `splitStyle` in `candidate-b-react-native/src/core/style.ts` replaces every URL of the scheme `g1bundle` by a file URL in the bundle directory and splits the bundle file `style.json`. The static sources and layers go to the `mapStyle` prop. The layers named in `metadata.runtime_floor_layers` and `metadata.runtime_language_layers` become `Layer` components placed with `afterId`. `layerFor` sets the floor filter (`withFloor`) and the label field (`textField`) from `state.floor` and `state.lang`. The route is a `GeoJSONSource` with the id `route`, fed with `state.routeFc`, which `routeFeatures` builds from the edge geometries. Rotation, tilt and the compass are off. The map is mounted again when `state.styleGeneration` changes (new bundle). `MapPanel` registers a `CameraPort` in `state.camera` (`easeTo`, `inspect`). `lonOf` and `latOf` in `candidate-b-react-native/src/state.ts` convert millimetres to map coordinates.

**Language.** `AppState.lang` starts as `ar`. `toggleLang` and `setLang` switch it and write `lang.changed`; no other state changes. `state.s` returns the `Strings` object of the language. `Strings.t(key, params)` fills `{name}` placeholders and returns `[key]` for a missing key. `Strings.rtl` comes from the key `_meta.direction`. `Root` sets the layout `direction`, and the component `T` sets text alignment and writing direction. Map labels follow through `layerFor`.

**Layout policy.** `layoutMode(width, height, fontScale)` in `candidate-b-react-native/src/core/policy.ts` returns `regular` when `width / fontScale >= 360` and `height / fontScale >= 600`, otherwise `compact`. `HomeScreen` passes the window of `useWindowDimensions()` minus the safe-area insets, and `fontScale`. Regular: the result list is a `FlatList` that scrolls inside its region and shares the free height with the map 2:3 (`flex: 2` and `flex: 3`). Compact: the whole home screen is one `ScrollView`, every result row is laid out, and the map height is `compactMapHeight(windowHeight)`, the smaller of 240 and half the window height. The other screens are a header and one `ScrollView` in both modes.

## 5. The native boundary

### 5.1 Where the boundary is defined

- Mechanism: one TurboModule named `NativeG1`, with codegen. `codegenConfig` in `candidate-b-react-native/modules/g1-native/package.json` names the spec library `G1NativeSpec`, the Java package `com.example.g1bench.g1native` and the iOS class `RCTNativeG1`.
- Spec file: `candidate-b-react-native/modules/g1-native/src/NativeG1.ts` (interface `Spec`). A method with a plain return type is synchronous (`nowNanos`, `echoSyncBase64`). A method that returns a `Promise` is asynchronous. The other methods return `void`.
- TypeScript side: `candidate-b-react-native/modules/g1-native/src/index.ts` exports `NativeG1`, `nowNanos`, `mark` and wrappers that parse JSON results (`ensureBundle`, `bundleInfo`, `validateQr`, `scanQr`, `launchCommand`). The application imports it as `g1-native`.
- Android side: class `NativeG1Module` in `candidate-b-react-native/modules/g1-native/android/src/main/java/com/example/g1bench/g1native/NativeG1Module.java` extends the generated class `NativeG1Spec`. `G1NativePackage` beside it registers the module, and `candidate-b-react-native/modules/g1-native/react-native.config.js` declares the package for autolinking. Each method calls the facade `G1Native` in `native-common/android/src/main/java/com/example/g1bench/common/G1Native.java`, except the two that hand a lab command to TypeScript (`launchCommand` and the handler of a new intent): they read the command with `LabCommand.fromIntent` of the shared module.
- iOS side: class `RCTNativeG1` in `candidate-b-react-native/modules/g1-native/ios/RCTNativeG1.mm` calls the Objective-C surface `G1NativeBridge` in `native-common/ios/Sources/G1NativeCommon/G1NativeBridge.swift`, which calls `G1Native` in `native-common/ios/Sources/G1NativeCommon/G1Native.swift`.
- Encoding: values are strings, numbers (doubles), booleans and arrays of them. Structured results are JSON strings. Binary data crosses as base64 strings, because the boundary has no binary type.
- Size and type checks: `validateQr` rejects a payload above 64 KiB, `echoAsyncBase64` a payload above the base64 size of 64 KiB and `importBundleBase64` a container above the base64 size of 64 MiB, each with `PAYLOAD_TOO_LARGE`. Base64 that does not decode gives `BAD_ARGUMENT`. `echoSyncBase64` returns an empty array instead of an error. A wrong argument type is a JavaScript `TypeError` before native code on Android (generated JSI layer); on iOS `RCTNativeG1` checks object arguments itself (`G1Str`, `G1OptStr`) and rejects with `BAD_ARGUMENT`.
- Events back to TypeScript: three codegen event emitters in the spec, `onCommand` (lab command), `onArEvent` (events of the AR screen as JSON) and `onN2R` (native-to-runtime echo messages). Native code sends them with `emitOnCommand`, `emitOnArEvent` and `emitOnN2R`. `LabController.start()` subscribes to the first two.

### 5.3 Adding or changing an operation across the boundary

The steps follow the existing operation `validateQr`.
1. Declare the method in `Spec` in `candidate-b-react-native/modules/g1-native/src/NativeG1.ts`. Choose a plain return type (synchronous), a `Promise` or `void`. Pass binary data as a base64 string and a structured result as a JSON string.
2. For a JSON result add a parsing wrapper in `candidate-b-react-native/modules/g1-native/src/index.ts`, as for `validateQr`.
3. Android: override the method in `NativeG1Module`. Check sizes with `tooLarge`, decode base64 with `base64`, call `G1Native`, then resolve the promise or call `promise.reject` with a code. The base class `NativeG1Spec` is not in the tree; the build generates it from the spec (block `react` in `candidate-b-react-native/modules/g1-native/android/build.gradle`).
4. iOS: add the method to `candidate-b-react-native/modules/g1-native/ios/RCTNativeG1.mm` with the selector that matches the spec, for example `validateQr:resolve:reject:`. Check object arguments with `G1Str` or `G1OptStr`, check sizes, then call `G1NativeBridge`. Add an `@objc` method to `G1NativeBridge` when the facade method is not exposed yet.
5. New native behaviour goes into the facade `G1Native` of the shared module on both systems. A change there affects all three applications that use the module.
6. Call the method from `AppState` or `LabController` through `G1.NativeG1` or the wrapper.
7. A new lab command needs five places: `LAB_COMMANDS` and the `exec` switch in `candidate-b-react-native/src/lab.ts`, `LabCommand.COMMANDS` (Java), `LabCommand.commands` (Swift; not for an Android-only command), and `lab_hooks.commands` in `contract/contract.json`.
8. Tests that cover the message decoder: the unit case `lab hooks: registered commands, UI script and envelope decoder match the contract` covers `decodeEnvelope` and the command list. The case `boundary encodings: CRC-32 check value, base64 engine and portable paths, UTF-8 replacement` covers the encodings. `LabCommandTest.transportAdmitsExactlyTheContractCommands` (Android) and `testLabCommandsAreRegisteredBoundedJsonObjects` (iOS) cover the native transport. The unit suite mocks `g1-native`, so it runs no native code.
9. Check the result with the unit suite, the release build and the hosted iOS job.

## 8. Diagnosing a problem

- Markers: one line each, `G1MARK v=1 app=B seq=<n> name=<name> t=<native ns> rt=<runtime ns or -> key=value ...`. Android: logcat tag `G1MARK`, priority INFO. iOS: unified log, subsystem `com.example.g1bench`, category `G1MARK`; lab builds also write the line to standard error. The names are in `markers.names` of `contract/contract.json`. Markers carry ids, codes and numbers only, never typed text.
- Markers written from TypeScript: `screen.shown`, `lang.changed`, `floor.changed`, `search.result` (`outcome`, `count`), `route.result` (`outcome`, `steps`), `map.style.loaded`, `fallback.shown`, `qr.result`, `update.state`, `a11y.seeded`, `map.camera.done`, `run.start`, `run.done`, `session.window`, `fuzz.progress`, `crash.trigger`, `command.rejected`, `command.failed`, and `bundle.loaded` with `state=PARSE_ERROR`.
- Markers written by the shared module: `app.start`, `app.ready`, `app.resume.ready`, `bundle.loaded`, `bundle.result`, `qr.validated`, `ar.state`, `ar.arrow`, `session.state`, `command.received`, `command.rejected`, `crash.trigger`.
- Lab hooks: the 25 names are in `LAB_COMMANDS` (`candidate-b-react-native/src/lab.ts`); arguments and effects are in `lab_hooks.commands` of `contract/contract.json`. The names: `nav.home`, `nav.details`, `nav.route`, `nav.open-route-ar`, `lang.set`, `search.set`, `map.inspect`, `map.camera`, `bundle.import`, `bundle.rollback`, `bundle.remove`, `bundle.update`, `qr.inject`, `ar.inject`, `session.start`, `session.end`, `session.status`, `a11y.seed`, `crash`, `fuzz`, `bridge.attack`, `bench.search-route`, `bench.bridge`, `bench.ui-session`, `bench.idle`.
- Invoking a hook on Android: two string extras on the launcher activity, `g1.cmd` (the name) and `g1.args` (a JSON object of at most 16 KiB). The lab sends `am start -n com.example.g1bench.candidateb/.MainActivity --es g1.cmd <name> --es g1.args <json>`. The activity is `singleTop`: a running application gets the command through `onNewIntent`, a new process through `launchCommand`. The shared class `LabCommand` refuses unknown names and writes `command.rejected`.
- Lab files on Android: the folders `import` (input) and `out` (results) under `g1` in the external files directory of the application (class `G1Files`). The lab uses the device path `/sdcard/Android/data/com.example.g1bench.candidateb/files/g1`. A hook with a `run_id` writes the file `<run_id>.json` into the `out` folder.
- On iOS a hook arrives as the launch arguments `-g1.cmd <name> -g1.args <json>`, or as a URL with the scheme `g1bench-b`, the host `cmd` and the items `name` and `args`. The files are under the folder `g1` of the application's Documents directory.
- Wrong search result: look at `normalize`, `tokens`, `codeKey` and the token set built in the `SearchIndex` constructor (`candidate-b-react-native/src/core/search.ts`). Run test case 1. On a device send `search.set` with `text` (Android only) and read `search.result`, `home.results.status` and the rows `home.result.<id>`.
- Wrong route: look at `RouteGraph.route` in `candidate-b-react-native/src/core/route.ts`. The constructor sorts the node ids, so the index order is the id order; on the same distance the smaller predecessor index wins, and `Heap` orders by distance, then by node index. The rejections are decided by further searches without the step-free flag or without the blocked edges. Run test case 2. On a device send `nav.route` with `case` (for example `RT01`) or with `destination`, `origin` and `step_free`, and read `route.result`. The hook `bench.search-route` runs every route case of the bundle through `computeRoute` and writes `nodes`, `length_mm`, `steps` and `summary` per case into its result file.
- Wrong step text: the step objects come from `routeSteps` (`candidate-b-react-native/src/core/steps.ts`). The text comes from `stepText`, `summaryText` and `rejectText` in `candidate-b-react-native/src/core/format.ts` with the keys `route.step.*`, `route.summary` and `route.reject.*`. The strings are copies of `contract/strings/`; test case 5 fails when they differ. The rows are `route.step.<index>` in `RouteScreen`; `FallbackScreen` shows the same steps.
- Wrong layout at a window size: check `layoutMode` and `compactMapHeight` with the window size and the text scale, then the two branches at the end of `HomeScreen` and the styles `results` (`candidate-b-react-native/src/ui/screens.tsx`) and `map`, `mapCompact` (`candidate-b-react-native/src/ui/MapPanel.tsx`). The rules are in `layout` of `contract/contract.json`; test case 7 holds the vectors.
- Map problem: check `map.style.loaded`. On Android send `map.inspect` with a `run_id`; it writes the camera, the declared floor and label field, and the rendered features per layer.
- A bridge call fails: read the rejection code (`PAYLOAD_TOO_LARGE`, `BAD_ARGUMENT`, `IO`, `UNSUPPORTED`). `command.rejected` with `reason=runtime_envelope` comes from `LabController.drain`; `command.failed` carries the command and the error name. On iOS `RCTNativeG1` observes lab URLs only after `setEventEmitterCallback:`; an emit through an instance without that callback aborts the process (comment in `candidate-b-react-native/modules/g1-native/ios/RCTNativeG1.mm`).
- No data after start: read the text of `home.trust` (`trustText`), `bundle.loaded` (`state`) and `bundle.result` (`code`). The codes are in the shared class `TrustCodes`.

## 10. Known limits

- Light appearance only (`platform_floor.appearance` in `contract/contract.json`).
- AR on an emulator or simulator leads to the text fallback: the Android emulator image has no ARCore and the iOS simulator has no world tracking, so the availability is `UNSUPPORTED` (`ArSupport` on both systems, `AppState.openAr`).
- A real AR session never establishes a pose and never shows the guidance arrow, because no spatial fixture exists (`ArActivity`, `ArViewController`). The injected mode (`ar.inject`) replays a state script without a camera and is labelled SIMULATED.
- Lab hooks are compiled into lab builds: `BuildFlags.LAB = true` (Java) and `BuildFlags.lab = true` (Swift, in `native-common/ios/Sources/G1NativeCommon/G1Files.swift`).
- Five hooks exist on Android only: `search.set`, `a11y.seed`, `bundle.remove`, `map.inspect`, `map.camera`. On iOS `removeBundles` rejects with `UNSUPPORTED`.
- The boundary has no binary type; payloads cross as base64. Numbers are doubles: nanosecond clock values stay exact below 2^53 ns, about 104 days of uptime (comment in `native-common/ios/Sources/G1NativeCommon/G1NativeBridge.swift`).
- On iOS the primitive arguments (BOOL, double) cannot be type-checked at the boundary (comment in `candidate-b-react-native/modules/g1-native/ios/RCTNativeG1.mm`).
- Network: only the lab update origin is used (`LAB_UPDATE_ORIGIN` in `candidate-b-react-native/src/state.ts`: HTTPS, `localhost`, port 8443); `AppState.update` rejects any other URL before it sends anything. `XMLHttpRequest` has no separate connect phase, so one 30 s inactivity watchdog covers connect and first byte. An update body above 64 MiB fails.
- The map binding has no getters for the gesture policy, the floor filter and the label field; `map.inspect` reports them as `declared`.
- The home search field is uncontrolled while the user types. On iOS, key events that arrive while React Native applies the first typed character again are discarded (comment in `candidate-b-react-native/src/ui/screens.tsx`).
- `candidate-b-react-native/ios/G1CandidateB/Info.plist` lists portrait and the two landscape orientations for the phone and all four orientations for the tablet, and sets the light interface style (`UIUserInterfaceStyle`).
- Release builds are signed with the debug signing configuration; there is no release identity.
- Synthetic data only. Not a product and not for navigation.
